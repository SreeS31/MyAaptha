Send only the Project ID and protected access reference; never paste passwords, tokens or service-account JSON. ## Prepared provisioning bundle

The generator makes no network calls. In a checked-out repository in Cloud Shell:

```bash
python3 infrastructure/gcp_beta.py --project ACTUAL_BETA_PROJECT_ID --output .tools/gcp-beta
cat .tools/gcp-beta/deployment-plan.json
```

Replace ACTUAL_BETA_PROJECT_ID with the real activated project ID. Review actual trial status, quota and the [project cost estimate](https://cloud.google.com/products/calculator) first. Configure project budget/credit alerts; [alerts-only budgets are not a spending cap](https://cloud.google.com/billing/docs/how-to/budgets). The profile uses one Mumbai `e2-standard-4` VM (4 vCPU, 16 GiB RAM), one retained 100 GB persistent boot disk, a dedicated VPC/subnet, a regional public IPv4 and only web/TURN ingress. This is a proposed small functional-beta profile, not a 5,000-user capacity claim or a guaranteed 90-day allowance.

After checking actual active trial status and sufficient credit, and reviewing the bundle, provisioning is:

```bash
MYAAPTHA_BETA_TRIAL_VERIFIED=yes bash .tools/gcp-beta/provision.sh
bash .tools/gcp-beta/address.sh
bash .tools/gcp-beta/access.sh
```

The generator cannot verify billing/trial status: the environment guard is an explicit operator attestation, not an automatic credit check. Without it the script exits before any gcloud call.

Provisioning is first-run only: existing resource names cause failure rather than silently adopting/changing them. Inspect partial progress before retrying. Every command pins the actual project. SSH is limited to IAP's IPv4 range and OS Login; no default VM service account or cloud scopes are attached. The operator needs project Compute/service-use provisioning permissions, OS Admin Login and IAP tunnel access. No broad IAM grants are created by this script.

The VM stops automatically after seven days of each run; it does not delete its boot disk. `bash .tools/gcp-beta/pause.sh` pauses compute earlier. **Retained disks and IPs can still consume credit while stopped.** An actual cost review and explicit cleanup plan remain required. The bundle never destroys data or disables billing.

## Candidate images

`.github/workflows/beta-images.yml` runs on `beta-*` tags, independently of production's `v*` tags. It requires the reusable CI suite, builds all three application images, checks runtime restrictions and blocks HIGH/CRITICAL findings before publishing `beta-<source SHA>` tags. It records image digests and SBOMs as `beta-release-*` artifacts. Deployment must use those immutable digests, not a moving beta tag. There is no cloud deployment or production promotion step in that workflow.

Engineering will point `beta.myaaptha.com` and `beta-turn.myaaptha.com` at the assigned beta IP after DNS delegation. These names are proposed; existing `www.myaaptha.com` is untouched. Use the existing `infrastructure/production/docker-compose.prod.yml`, `compose.single-host.yml`, `compose.integrations.yml` and `compose.call-relay.yml` profiles with a **separate beta working directory, keys, volumes and Compose project name `myaaptha-beta`**. Never copy production records or reuse an existing database volume.

Before starting, prepare immutable dependency images, internal PostgreSQL/Redis TLS/CA material and actual beta-only application secrets. Keep the database/cache/ClamAV and object store off public host ports. Configure a private encrypted **S3-compatible** store (for example TLS-enabled MinIO on the beta VM with persistent storage and separate scoped credentials). Native Google Cloud Storage is not a drop-in configured backend in this repository; do not point the S3 adapter at an untested GCS endpoint. Validate the [90-day versioning/recovery policy](RECOVERY-POLICY-2026-11-09.md), runtime IAM and isolated restore before claiming recovery support. The private object store provisioning, TLS, IAM and runtime credentials still require actual setup; no completed Compose render or deployed storage is claimed here.

Use `docker compose ... config --quiet` to validate without printing interpolated secrets. Start the dependency services and migration/encryption jobs before the backend; preserve existing scanner, database TLS, cookie, CORS and secret-strength checks. Set the real beta origin and gateway/frontend proxy addresses. The web uses same-origin `/api` routing; Android builds use `--dart-define=API_BASE_URL=https://beta.myaaptha.com`. Rebuild mobile artifacts for that URL; existing local-network APKs are not beta-ready. Firebase App Distribution can deliver the Android beta after its project is connected. iOS still needs Mac/Xcode, signing and device acceptance.

The approved 90-day file recovery duration, uploader expiry choices/Never, 1 GB initial quota and 100 GB paid cap remain unchanged. Hosting credits do not configure SMS, email, OAuth, AI, TURN credentials or push tokens. Health processing stays disabled until its provider/consent/quality acceptance; test its unavailable state first, then perform real-provider acceptance before calling the complete beta passed.

## Beta acceptance and promotion boundary

Start with synthetic accounts/files and controlled physical Android/browser sessions. Run login/recovery, data reload after server/client restart, web/native synchronization, owner/cross-account denial, uploads/scanning/expiry, calling across Wi-Fi/mobile networks, real notification delivery, backup/restore and monitoring. Record exact image digests, APK hash/API URL, endpoints and results in the existing acceptance matrix. A time-limited beta cannot demonstrate 90 days of elapsed lifecycle behavior; record configuration/readback and synthetic restore separately. Passing beta functional checks does not close final production capacity, independent review or owner-promotion gates.
